Code Review

A code review is the process of having one or more developers examine 
someone else's code before it is merged into the main codebase.
The goal is to improve code quality, catch bugs, ensure consistency, 
and share knowledge across the team.

Code review is a quality assurance practice where developers inspect each other's code 
to identify defects, improve design, maintain coding standards, 
and ensure the code is ready to be merged into the project.


Why code reviews are important

Code reviews help teams:

Find bugs early before they reach production.
Improve code quality by suggesting cleaner, simpler, or more efficient solutions.
Maintain coding standards so the codebase stays consistent.
Share knowledge by exposing team members to different parts of the codebase.
Reduce technical debt by preventing poor design decisions from accumulating.


How a typical code review works
A developer writes code for a feature or bug fix.
They create a pull request (PR) or merge request (MR).
One or more teammates review the changes.
Reviewers leave comments, ask questions, or suggest improvements.
The author updates the code if needed.
Once approved, the code is merged into the main branch.

What reviewers look for

A reviewer typically checks:

Correctness: Does the code solve the problem?
Readability: Is it easy to understand?
Maintainability: Will it be easy to modify later?
Performance: Are there unnecessary slow operations?
Security: Could the code introduce vulnerabilities?
Testing: Are there adequate tests for the changes?
Style: Does it follow the team's coding conventions?


Best practices for code reviews

For authors:

Keep pull requests small and focused.
Write clear descriptions explaining the changes.
Respond respectfully to feedback.
Add or update tests when necessary.


For reviewers:

Be constructive and respectful.
Explain why a change is recommended.
Focus on important issues rather than personal preferences.
Acknowledge good code as well as areas for improvement.

Learn to Spot Code Smells

Here are common ones you'll begin to recognize with practice.

Smell	                Why it's a problem
Giant functions	        Too many responsibilities
Deep nesting	        Hard to follow
Repeated code	        Bug fixes must be duplicated
Magic numbers	        Meaning is unclear
Long parameter lists	Hard to use correctly
Boolean flags	        Often indicate multiple responsibilities
Global state	        Difficult to reason about
Side effects	        Unexpected behavior
Hidden dependencies	    Hard to test
Inconsistent naming	    Increases cognitive load



Learn to Ask Better Questions

Instead of

This is wrong.

Say

What happens if the user submits this request twice?

Instead of

Refactor this.

Say

Could we extract this validation into a reusable helper so it's shared with the update flow?

Instead of

Bad naming.

Say

Would calculateInvoiceTotal communicate the intent more clearly than processInvoice?

Great reviewers coach rather than dictate.



Prioritize Your Feedback

A useful framework is:

Blocker – Must be fixed before merging (bugs, security issues, broken logic, data corruption).
Major – Strongly recommended before merging (maintainability, missing tests, architectural issues).
Minor – Can be addressed later (small refactors, naming improvements, formatting).
Nit – Purely stylistic suggestions that don't affect correctness.

This helps authors understand what truly matters.


Build a Review Checklist

Over time, you'll internalize these questions:

Does it solve the requirement?
Is the design appropriate?
Is it correct?
Are edge cases handled?
Is it secure?
Is it performant enough?
Is it maintainable?
Is it readable?
Are tests sufficient?
Is the change scoped appropriately?

A checklist keeps reviews consistent and prevents you from focusing only on style.


A 10-Week Learning Plan

Weeks 1–2: Focus on correctness and business logic. Ignore formatting almost entirely.

Weeks 3–4: Learn to identify maintainability problems, code smells, and responsibility boundaries.

Weeks 5–6: Study testing. For every change, think about the happy path, edge cases, and failure cases.

Weeks 7–8: Learn performance fundamentals (database access patterns, algorithms, memory usage) 
and common security pitfalls.

Weeks 9–10: Practice writing high-quality review comments that are clear, 
actionable, and respectful. Aim to explain why a change is needed, not just what to change.

The Mental Models of Great Reviewers

These are the questions that experienced reviewers instinctively ask.

Invariants

What must always be true?

Example:

An order cannot be both "Cancelled" and "Paid."

Does this change preserve that rule?

Preconditions

What must be true before this code runs?

User must exist.

Is that guaranteed, or just assumed?

Postconditions

What should be true after this function finishes?

Inventory count must never be negative.

Can this function violate that?

Failure Domains

If this component fails, what else breaks?

A logging failure should not prevent a user from checking out. A payment service failure probably should.

Blast Radius

If this code is wrong, how many users are affected?

A typo in an internal admin page has a small blast radius. A bug in authentication or payments has a huge one.

Coupling

How many other components must change if this code changes?

High coupling is a warning sign. Favor designs where changes stay localized.

Cohesion

Does this module have one clear responsibility?

If a class validates input, sends emails, updates the database, and formats reports, it's trying to do too much.

Complexity Budget

Every new abstraction has a cost. Ask whether it genuinely simplifies the system or just moves complexity elsewhere.
