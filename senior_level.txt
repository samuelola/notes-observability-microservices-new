3. Understand what happens when the worker crashes

Suppose the worker is processing:

note.created email job

and crashes.

Laravel's queue system uses a visibility/attempt mechanism so a job
that wasn't successfully completed can become available again.

The lifecycle is roughly:

Redis
  │
  ▼
Worker receives job
  │
  ▼
Job processing
  │
  ├── SUCCESS ──────→ job removed
  │
  └── FAILURE
          │
          ▼
       retry
          │
          ▼
       attempts++

So you should not manually delete jobs from Redis when a worker fails.

4. Configure retry_after

This is very important.

In config/queue.php, your Redis connection should have something like:

'redis' => [
    'driver' => 'redis',
    'connection' => 'default',
    'queue' => env('REDIS_QUEUE', 'default'),
    'retry_after' => 90,
    'block_for' => null,
],

Then:

worker --timeout=60
retry_after=90

The general rule is:

retry_after must be greater than the worker timeout.


If:

retry_after = 60
timeout = 60

you can get into ugly situations where the same job 
becomes available while the original worker may still be finishing it.

Use enough margin.


5. Don't make retry_after too small

Bad:

--timeout=60
retry_after=30

Potentially:

Worker A starts job
       ↓
30 seconds
       ↓
job becomes available again
       ↓
Worker B gets same job
       ↓
Worker A still working
       ↓
duplicate processing

Better:

--timeout=60
retry_after=90

Row locking

DB::transaction(function () use ($fromId, $toId, $amount) {

    $from = Account::where('id', $fromId)
    ->lockForUpdate()
    ->first();

    $to = Account::where('id', $toId)
        ->lockForUpdate()
        ->first();

});


This code above causes row deadlock


But another person could be doing:

fromId = 20
toId = 10

They would lock:

20 → 10

Now we have the problem:

Request 1                 Request 2

Lock 10 🔒                Lock 20 🔒
   ↓                         ↓
Wants 20 ⏳                Wants 10 ⏳
   ↓                         ↓
   └────── DEADLOCK 💥 ──────┘


To avoid deadlock

Don't lock based on FROM and TO. Lock based on ID order.

Always:

smaller ID → bigger ID


DB::transaction(function () use ($fromId, $toId, $amount) {

    // 1. Decide which account to lock first
    //    Always smaller ID first.
    $firstId = min($fromId, $toId);
    $secondId = max($fromId, $toId);

    // 2. Lock the first account
    $first = Account::where('id', $firstId)
        ->lockForUpdate()
        ->firstOrFail();

    // 3. Lock the second account
    $second = Account::where('id', $secondId)
        ->lockForUpdate()
        ->firstOrFail();

    // 4. Figure out which locked account is FROM
    $from = $fromId === $firstId ? $first : $second;

    // 5. Figure out which locked account is TO
    $to = $toId === $firstId ? $first : $second;

    // 6. Take money from FROM
    $from->decrement('balance', $amount);

    // 7. Give money to TO
    $to->increment('balance', $amount);
});

So one request may wait, but they don't create the circular waiting that causes this deadlock.

One sentence to remember (NB)

When a transaction needs to lock multiple rows, 
make every transaction lock those rows in the same order.

12. Pagination

Note::latest()->paginate(20);

But eventually you need to understand what happens when you're requesting:

page = 100000

MySQL may need to walk past huge numbers of records.

Laravel can provide:

Previous | 1 | 2 | 3 | 4 | Next

Imagine you have 10 million notes.

With normal pagination:

Note::latest()->paginate(20);

When you request a very late page, such as page 500,000, 
the database may have to skip a huge number of records.

Page 500,000
↓

↓

Cursor pagination works more like:

Last ID seen = 10,000,000
↓
find records after/before this position
↓
give me 20

Instead of page numbers, you typically get:

Laravel uses a cursor representing the position of the last item.

Database constraints

Senior engineers don't rely exclusively on application code.

For example, don't rely on:

if (! User::where('email', $email)->exists()) {
    User::create([...]);
}

Two requests can race.

Instead, enforce the invariant at the database level:

$table->string('email')->unique();

Likewise:

$table->foreignId('user_id')
    ->constrained();

and:

$table->string('event_id')->unique();



$table->index(['user_id', 'created_at']);

is appropriate for:

SELECT *
FROM notes
WHERE user_id = 5
ORDER BY created_at DESC
LIMIT 20;

If Auth owns users and Notes has a separate database, do not create a MySQL foreign key across services.

In that case:

$table->unsignedBigInteger('user_id');

is perfectly reasonable, and the application/event architecture maintains that relationship.

| -------------- | ------------------------- | ----------------------------------- |

| Component | Responsibility                                 |

Redis failure
     ↓
TransientInfrastructureException
     ↓
RabbitMQ retry
     ↓
Redis recovery
     ↓
process again

That's exactly the failure separation you've been implementing.

Worker failure

Suppose Redis accepted the job:

Redis
  ↓
Email Worker
  ↓
Worker crashes

The job should remain recoverable according to the queue's acknowledgment/visibility semantics.

So the architecture needs to distinguish:

job accepted

from:

job successfully executed

That's the next important design concept.

2. Client security

The client should never directly access RabbitMQ, Redis, or MySQL.

Bad:

Client ───────► MySQL
Client ───────► Redis
Client ───────► RabbitMQ

Correct:

Client ──HTTPS──► Application
                     │
                     ├──► MySQL
                     ├──► Redis
                     └──► RabbitMQ

This gives the application a security boundary.

The client only gets access to API endpoints.


3. Authentication

For your Laravel application, the basic flow is:

Client
   │
   │ credentials
   ▼
API
   │
   ▼
Authentication
   │
   ├── valid ──► authenticated user
   │
   └── invalid ► 401

After authentication, every request should have an authenticated identity.

For example:

User #15

Then authorization determines whether User #15 can perform the requested operation.


4. Authorization

Authentication answers:

Who are you?

Authorization answers:

Are you allowed to do this?

For your Notes system:

GET /notes/123

should not simply mean:

SELECT * FROM notes WHERE id = 123;

It should enforce ownership:

SELECT *
FROM notes
WHERE id = 123
  AND user_id = 15;

This is extremely important.


This is extremely important.

Otherwise:

User A
   │
   │ GET /notes/123
   ▼
Application
   │
   ▼
Note #123 belongs to User B
   │
   ▼
❌ Data leak


Your existing repository method:

Note::where('id', $id)
    ->where('user_id', $userId)
    ->firstOrFail();

is therefore doing something security-critical: tenant/resource isolation.


5. Input validation

Never trust client input.

For example:

{
    "title": "...",
    "content": "..."
}

The server should validate:

title
 ├── required
 ├── string
 ├── maximum length
 └── acceptable format

content
 ├── required
 ├── string
 └── maximum length

Security boundary:

UNTRUSTED INPUT
      │
      ▼
VALIDATION
      │
      ▼
APPLICATION

Don't rely on the frontend for validation.


6. SQL injection

Your application should use parameterized queries.

Laravel's query builder/Eloquent handles this for normal queries:

Note::where('user_id', $userId)->get();

Conceptually this becomes:

SELECT *
FROM notes
WHERE user_id = ?;

rather than constructing:

SELECT *
FROM notes
WHERE user_id = '$userId';

Never concatenate untrusted input into SQL.


7. RabbitMQ security

RabbitMQ is an internal infrastructure component.

It should not be publicly exposed.

Think:

Internet
   │
   X
RabbitMQ

Instead:

Application network
        │
        ▼
    RabbitMQ

Use RabbitMQ credentials with the minimum permissions required.

Ideally separate credentials by application/service.

For example:

notes-service
email-service

should not necessarily share one powerful RabbitMQ account.

8. RabbitMQ message security

Remember that messages are also untrusted input.

Even though RabbitMQ is internal, your consumer should validate the message.

For your event:

{
    "event_id": "...",
    "event": "note.created",
    "user_id": 15,
    "note_id": 123
}

The consumer should verify:

event exists
event_id exists
event type is expected
user_id is valid
note_id is valid
required fields exist

Then:

RabbitMQ message
       │
       ▼
Validate
       │
       ├── invalid ──► Business failure / DLQ
       │
       └── valid ────► process


9. Replay protection

This connects directly to the idempotency work you already did.

Suppose RabbitMQ delivers:

event_id = abc123

twice.

Without protection:

abc123
  │
  ├──► send email
  │
  └──► send email again

With idempotency:

abc123
  │
  ▼
ProcessedEvent?
  │
  ├── YES ──► ACK
  │
  └── NO  ──► process

This is both a reliability and security concern because replayed messages can cause duplicate side effects.


10. Redis security

Redis should also be internal.

Internet
   │
   X
Redis

The application talks to Redis:

Application
     │
     ▼
   Redis

Don't expose Redis directly to clients.

Redis may contain things such as:

sessions
cache
rate-limit counters
queue data
temporary state

So compromise of Redis can have serious consequences.


11. Rate limiting

Redis becomes particularly useful here.

For example:

POST /login

You could maintain a counter:

login_attempts:user/ip

Conceptually:

Request
   │
   ▼
Redis counter
   │
   ├── under limit ──► application
   │
   └── over limit ───► 429

Example policy:

5 login attempts / minute

The exact limits should be chosen based on your application rather than hard-coded as a universal rule.


12. MySQL security

The application should use a dedicated database user.

Avoid:

Laravel → root

Prefer:

Laravel → application_db_user

with only the privileges the application actually requires.

Also:

Internet
   X
MySQL

MySQL should be accessible only from the application/network where necessary.


13. Secrets

Do not put credentials directly into source code.

Bad:

$password = 'my-secret-password';

Use environment/configuration:

DB_PASSWORD=...
RABBITMQ_PASSWORD=...
REDIS_PASSWORD=...

And protect the environment/secrets store.

The source repository should contain:

code
configuration templates

not production credentials.


TLS encrypts information while it travels from one machine to another.


1. What does "data while moving" mean?

Suppose your browser sends your password to your API:

Browser
   │
   │  username + password
   ▼
API

That information is traveling through a network.

Without encryption, someone who can intercept the network traffic might be able to read it.


With HTTPS/TLS:

Browser
   │
   │ 🔒 encrypted
   ▼
API

The attacker might see that communication is happening, but should not be able to read the protected contents.

2. HTTPS is HTTP + TLS

When you see:

https://example.com

the https means the HTTP communication is protected using TLS.

So:

HTTP
  +
TLS
  =
HTTPS

For example:

Client ─── HTTPS/TLS ───► API

Your API receives the decrypted HTTP request.


3. What about RabbitMQ, Redis and MySQL?

This is where the infrastructure part comes in.

Imagine your application is running in one container/server and RabbitMQ is running somewhere else:

Application
     │
     │ RabbitMQ connection
     ▼
RabbitMQ

The application might send:

UserCreated
{
    "id": 123,
    "email": "samuel@example.com"
}

If the connection is not encrypted, that information travels across the network without TLS protection.

With TLS:

Application
     │
     │ 🔒 encrypted
     ▼
RabbitMQ

The same idea applies to Redis:

Application
     │
     │ 🔒 TLS
     ▼
Redis


And MySQL:

     │
     │ 🔒 TLS
     ▼
MySQL

15. Logging without leaking secrets

Your logs are also a security boundary.

Avoid:

Log::info('Request', [
    'password' => $password,
    'token' => $token,
]);

Likewise, be careful with your RabbitMQ logs.

You currently log message bodies in some failure paths:

'message' => $message->body,

That can become a security problem if events eventually contain sensitive information.

Prefer logging identifiers:

event_id
event_name
user_id
note_id
retry_count
exception type

rather than the entire payload.
