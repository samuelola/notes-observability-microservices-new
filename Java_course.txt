Phase 5 — The interesting part: money transfers

We'll implement:

POST /api/transfers
{
  "sourceAccountId": "acc_001",
  "destinationAccountId": "acc_002",
  "amount": 50000,
  "currency": "NGN"
}

The system needs to guarantee things like:

Source:      ₦100,000
Transfer:     ₦50,000
Destination:  ₦20,000

                    ↓

Source:      ₦50,000
Destination: ₦70,000

And if something fails halfway through, we must not end up with:

Source:      ₦50,000
Destination: ₦20,000

That's where database transactions become extremely important.

Phase 6 — Concurrency

This is where you'll start thinking like a serious backend engineer.

Imagine two requests arrive simultaneously:

Request A: Transfer ₦80,000
Request B: Transfer ₦80,000

The account contains:

₦100,000

Without proper concurrency control, both requests might see:

Balance = ₦100,000

and both conclude:

"There is enough money."

You could accidentally allow:

₦100,000
     ↓
- ₦80,000
- ₦80,000
     ↓
- ₦60,000

Obviously unacceptable.

We'll learn:

Race conditions
Isolation levels
Row locking
Optimistic locking
Pessimistic locking
Atomic database operations
Deadlocks
Retry strategies

This is one of the biggest differences between simply knowing a framework and understanding software engineering.

Phase 7 — Idempotency

Suppose the client sends:

POST /api/transfers
Idempotency-Key: abc123

The request succeeds.

But the network fails before the client receives the response.

The client retries.

Without idempotency:

₦50,000
   ↓
Transfer #1

₦50,000
   ↓
Transfer #2

The customer loses ₦50,000 twice.

With idempotency:

Request #1
    ↓
abc123
    ↓
Transfer created

Request #2
    ↓
abc123
    ↓
Return existing transaction

No duplicate transfer.

This is extremely important in financial APIs.

Phase 10 — Kafka

Now we'll move beyond a simple application.

When a transfer succeeds:

Transfer Service
       │
       ▼
    Kafka
       │
 ┌─────┼───────────┐
 ▼     ▼           ▼
Audit  Notification Fraud
Service Service    Service

Instead of the transfer service directly calling everything:

Transfer
   ↓
Audit
   ↓
Email
   ↓
SMS
   ↓
Fraud

we can publish an event:

{
  "event": "TRANSFER_COMPLETED",
  "transactionId": "tx_123",
  "amount": 50000,
  "currency": "NGN"
}

Other services can consume it.

That's where you'll start learning event-driven architecture and distributed systems.
